# Technology Stack

## Backend

### Framework: FastAPI

**Why over Django Ninja (current stack):**

- **Clean break from Django ORM** — the source of most architectural pain. No GenericForeignKey, no ContentTypes, no multi-table inheritance, no implicit JOINs.
- **Async-native** — every endpoint is `async def` by default. I/O-heavy provider calls (TMDB, Steam, IGDB) benefit from non-blocking concurrency.
- **Pydantic v2** — type-safe request/response schemas that auto-generate OpenAPI. A single `BaseModel` is both a validation schema and API documentation.
- **Dependency injection** — `Depends(get_db)`, `Depends(get_current_user)`, `Depends(get_media_service)` are cleaner than Django middleware stacks for auth, sessions, rate limiting.
- **No Django admin dependency** — the admin is tightly coupled to Django's ORM and template system. Replace with a lightweight alternative or skip entirely.

**What we lose from Django:**
- Django admin (rebuild or replace with SQLPage/Retool if needed)
- Django's built-in migration autodetector (Alembic requires explicit migration writing)
- Django REST Framework's browsable API (FastAPI has Swagger UI, which is comparable)

### ORM: SQLAlchemy 2.0 (async)

**Why over Django ORM:**

- **Explicit relationships** — every FK is declared in the model, not inferred through `content_type_id` + `object_id`
- **No GenericForeignKey** — the single biggest data model improvement. Every relation is a direct column reference.
- **Async session** — `AsyncSession` integrates natively with FastAPI's async handlers
- **Alembic** — mature migration tool, though more manual than Django's auto-detection

### Task Queue: Celery (simplified)

**Why keep Celery instead of migrating to asynq/Redis Streams:**

- Celery isn't broken — the 30 queues and complex routing function were the problem
- Migration risk is real — Celery has edge cases around retries, acks, and visibility timeouts that a new queue system would need to rediscover
- Simplifying to 7 queues with prefix-based routing gives the same benefit with zero migration risk

### Auth: JWT

**Why over PASETO:**

- PASETO solves JWT vulnerabilities (alg=none, weak HMAC keys) that are trivially avoided by using a mature library (PyJWT) with proper configuration
- JWT has a massive ecosystem of client libraries, debugging tools, and operational knowledge
- The PASETO Python library ecosystem is tiny — one primary library with limited community support

**Token architecture:**

| Token | Storage | Lifetime | Purpose |
|---|---|---|---|
| Access token | Browser memory (closure var) | 15 min | API authorization |
| Refresh token | HTTP-only cookie, SameSite=Lax | 7 days | Obtain new access tokens |

### Search: PostgreSQL tsvector

**Why not Elasticsearch/Meilisearch immediately:**

- tsvector with GIN index handles the current search volume
- No additional infrastructure to manage
- Swap for Meilisearch later when faceted search or typo tolerance becomes necessary

### Real-time: SSE

**Why over WebSocket:**

- All real-time needs are unidirectional (server pushes sync progress, notifications)
- SSE works over standard HTTP, no upgrade handshake, works through all proxies
- Simpler client: `EventSource` API vs WebSocket state machine
- Django Channels (WebSocket) gets deleted

## Frontend

### What Stays

| Layer | Technology | Notes |
|---|---|---|
| Framework | React 19 | Current version, no change |
| Build tool | Vite | Kept as-is |
| Router | TanStack Router | Route definitions, code splitting, auth guards all preserved |
| Data fetching | TanStack Query | Query key structure stays, hooks get rewritten for new client |
| Styling | Tailwind CSS 4 | Keep utilities, drop SCSS mixins |
| Components | All atoms, molecules, templates, organisms | No UI rebuild needed |

### What Changes

| Layer | Before | After |
|---|---|---|
| API client | axios + manual interceptors | `@otix/api-client` generated by openapi-typescript |
| Case conversion | snake_case ↔ camelCase interceptor | Type-safe generated client handles this |
| Auth headers | CSRF token + session cookie | `Authorization: Bearer <jwt>` header |
| Auth state | Django session | JWT access token in memory, refresh in cookie |
| Provider nesting | 8 levels deep | Flattened to 5 levels |
| Virtual scrolling | react-virtualized | @tanstack/react-virtual |

## Infrastructure

| Component | Choice | Why |
|---|---|---|
| Database | PostgreSQL 16 | tsvector, JSONB, GIN indexes, proven |
| Cache / Broker | Redis 7 | Celery broker, rate limiting token buckets, session cache |
| Deployment | Docker Compose + Dokploy | No Kubernetes overhead for a single-team project |
| CI/CD | GitHub Actions | Lint, type-check, test, build images, deploy webhook |
| Monitoring | Prometheus + Grafana | Metrics from FastAPI, Celery, PostgreSQL |

## Rejected Alternatives

| Decision | Alternative | Reason Rejected |
|---|---|---|
| Go backend | FastAPI | Solo dev with Python expertise. Learning idiomatic Go + translating domain logic = project-killing risk. |
| PASETO | JWT | Solves non-problems. Tiny library ecosystem. |
| Spec-first OpenAPI | Code-first | Hand-authoring YAML is tedious. ogen (Go codegen) less mature than FastAPI's auto-generation. |
| asynq | Celery | Celery isn't broken. Queue system migration adds risk with no benefit. |
| Full UI rebuild | Keep components | React components are well-built. Rebuilding them is busywork. |
| Next.js | Vite SPA | Auth-walled dashboard. SSR provides negligible benefit for logged-in content. |
| Kubernetes | Docker Compose | Massive overhead for a solo-dev, single-team project. |
